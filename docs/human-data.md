# Receiving and managing human results locally

For manual filing, keep one numbered folder per participant and use
`scripts/render_scene.py` to render its JSON files beside the originals. The
optional `scripts/human_results.py` workflow below provides automatic intake and
session-based archives instead. Both use the shared browser renderer; neither
calls a model, uploads results, or changes the published experiment.

## Numbered participant folders (manual workflow)

Save each complete result as a separate UTF-8 file, preserving all fields:

```text
result-data/human/
  0001/
    euro.json
    zhu.json
    euro.png                         Generated by the command below
    zhu.png                          Generated by the command below
  0002/
    ...
```

The researcher assigns the folder number. It does not replace the session or
trial IDs inside the received JSON. Keep self-tests in `result-data/human/self-test/`.

From the repository root:

```sh
PLAYWRIGHT_BROWSERS_PATH=/private/tmp/foodface-agent-browsers \
  /private/tmp/foodface-agent-venv/bin/python scripts/render_scene.py \
  result-data/human/0001
```

This reads all `.json` files directly inside `0001` (not subfolders), checks all
scenes and output paths before launching Chromium, and saves matching `.png`
files in the same folder. Keep only scene JSONs in that folder; store notes as
text rather than unrelated JSON files. JSON sources are never rewritten, and
existing PNGs are never overwritten. If rendering fails partway through, completed
PNGs remain; render each remaining JSON individually to resume:

```sh
PLAYWRIGHT_BROWSERS_PATH=/private/tmp/foodface-agent-browsers \
  /private/tmp/foodface-agent-venv/bin/python scripts/render_scene.py \
  result-data/human/0001/zhu.json
```

For a fresh rendering when a PNG already exists, use a single JSON with
`--output /absolute/path/to/new-name.png`. Numbered folders are managed manually;
`human_results.py list` lists only its own session-based archives, not these folders.

## Optional automatic intake

From the repository root, set up this terminal session:

```sh
export PLAYWRIGHT_BROWSERS_PATH=/private/tmp/foodface-agent-browsers
foodface_python=/private/tmp/foodface-agent-venv/bin/python
```

Copy **one complete JSON result** from the participant's message, then run:

```sh
"$foodface_python" scripts/human_results.py import --clipboard --collection formal
```

The command archives the JSON and renders a PNG automatically, printing their
locations. Repeat for the other portrait. Do not concatenate two JSON objects,
include Markdown code fences, or include surrounding message text. Copying from
the website's **Copy JSON** button best preserves valid JSON whitespace.

For an existing UTF-8 file (without BOM), use:

```sh
"$foodface_python" scripts/human_results.py import --file /absolute/path/result.json --collection formal
```

To save without starting a browser, add `--no-render`. Archiving and listing
require only Python's standard library. Rendering also needs the existing
[Playwright/Chromium environment](agent-workflow.md#setup-and-demo). The temporary
environment under `/private/tmp` may need to be recreated if the system clears it.

Use `--collection self-test` for personal tests. Existing files under
`result-data/local-validation/` are not automatically imported or reclassified.
Collection membership is a researcher decision, not inferred from demographic
values. Never import a known self-test into `formal`.

## Storage

Formal results are stored directly under `result-data/human/`; the `formal`
collection option does not create an extra directory.

```text
result-data/
  local-validation/                  Earlier personal tests, kept separate
  human/
    session-<sessionId>/
      zhu-<trialId>/
        original.json              Exact received UTF-8 bytes; never rewritten
        receipt.json               Intake time, classification, source hash
        renders/
          <UTC timestamp>-<id>/
            result.png             Original-resolution derived image
            render.json            Source/image hashes, renderer and browser details
      euro-<trialId>/
        ...
    self-test/                       Same layout, excluded from formal analysis
```

Keep `original.json` immutable. Demographics, feedback, timestamps, session IDs,
trial IDs, and any additional source fields are retained. Render input uses only
the validated scene fields. The archive records reception separately from the
participant's browser-generated `submittedAt`.

Identical repeated submissions (including JSON whitespace changes) reuse the
existing record. The first received bytes and receipt remain unchanged. A repeated
`trialId` with different content is rejected even if its `sessionId` changed;
resolve that discrepancy with the sender instead of replacing the original.
Different trials for the same portrait/session remain separate, visible records.

## Check completeness and render again

```sh
"$foodface_python" scripts/human_results.py list --collection formal
```

The list shows session IDs, the number of `zhu` and `euro` results in each session,
full trial IDs, archive paths, and render counts or `PENDING RENDER`. A session with
`zhu=1, euro=1` has one result for each portrait. A zero indicates a missing
portrait; a count above one needs review rather than automatic selection.

A session is **not** a verified participant identity. Refreshing creates a new
session, and personal details may differ between portraits because the form can
be edited before the second submission. Do not merge sessions or discard results
based on demographics alone.

To render an archived trial, substitute its full trial ID from the list:

```sh
"$foodface_python" scripts/human_results.py render FULL-TRIAL-UUID --collection formal
```

Each explicit render creates a new timestamped directory; existing PNGs remain
intact. A duplicate import with an existing PNG does not render again. If a browser
or rendering error occurs, the received JSON remains archived; use `render` to
retry. Incomplete render staging directories are not counted as finished images.
If the archived source hash no longer matches the receipt, rendering stops rather
than silently using edited data.

The PNG path is printed after success. On macOS, open it with:

```sh
open /absolute/path/to/result.png
```

## Backup and reproducibility

`result-data/` is ignored by Git. Keeping files inside this checkout does **not**
back them up to GitHub. Back up the complete private data directory separately,
including originals, receipts, PNGs, and render records. Publish only website
source/assets, never these records; do not force-add the directory to Git or copy
it into a public deployment package.

Each render records exact source/asset hashes, the Playwright version, and the
Chromium version. These identify the rendering environment but do not archive it.
Retain a matching project checkout/assets and dependency versions alongside the
private backup if future exact reproduction is required. Re-rendering with changed
assets or another browser version may produce different pixels; compare render
records when investigating differences.

The optional global `--data-root /absolute/private/path` flag selects a different
archive root for all commands. The default remains `result-data/human` in this
repository. This is a local file-management workflow, not a submission server or
an analysis pipeline; inclusion/exclusion decisions remain separate research work.
